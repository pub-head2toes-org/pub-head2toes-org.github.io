     Bandage UPDATE 1 — the recorder

     Context

     src/fs/pwa/bandage/ is a 25-key piano over a vendored webaudio-tinysynth.
     PLAN.md deliberately left the upper third of the screen empty and listed
     the
     recorder as the next piece of work. UPDATE_1.md asks for it: four loop
     channels, each recordable, playable in the background under the live keys,
     and
     editable as a grid of notes.

     Outcome: the reserved panel stops being reserved. It becomes a 4-loop
     transport
     you can record into while you play, plus a step editor, plus save/load as a
     standard MIDI file.

     What tinysynth can and cannot do here

     loadMIDI() (webaudio-tinysynth.js:842) ends with this.reset(); 
     this.locateMIDI(0); — it resets all 16 channels, allSoundOffs every one of
     them, and the synth holds exactly one song. So its SMF player cannot host
     four independently started loops beside a player's hands: starting loop 3
     would
     silence loops 1, 2 and whatever the fingers were holding, and reset the
     voice.

     So the transport is our own, and SMF is the file format rather than the
     engine:

     ┌──────────────┬──────────────────────────────────────────────────────────┐
     │     Job      │                           How                            │
     ├──────────────┼──────────────────────────────────────────────────────────┤
     │ Loop         │ Own look-ahead scheduler → synth.noteOn(ch, n, v, t)     │
     │ playback     │                                                          │
     ├──────────────┼──────────────────────────────────────────────────────────┤
     │ Save         │ Encode the four loops as a type-1 .mid                   │
     ├──────────────┼──────────────────────────────────────────────────────────┤
     │ Load         │ Feed the bytes to synth.loadMIDI(), read back            │
     │              │ synth.song.ev                                            │
     └──────────────┴──────────────────────────────────────────────────────────┘

     noteOn(ch,n,v,t) takes an absolute AudioContext time (_tsConv,
     webaudio-tinysynth.js:1017), which is what makes accurate scheduling
     possible
     without touching the library.

     Model

     - 4 loops, MIDI channels 1–4. Live keys keep channel 0 (CHANNEL in
     bandage.js), so the player's hands are never disturbed by a loop.
     - One loop = one MIDI channel = one instrument, taken from the Voice
     selector at the moment Record is pressed. A channel is polyphonic, so "up
     to
     4 notes at once" needs no extra plumbing.
     - A loop is a list of steps; a step holds up to 4 notes (or none — a rest).
     Length is rounded up to a whole bar of 16 steps, so loops of different
     lengths
     stay phase-locked.
     - One global step clock drives every loop: loop n sounds
     steps[globalStep % steps.length]. That is how a drum machine behaves and it
     keeps four transports honest with one counter.

     Files

     New — src/fs/pwa/bandage/loops.js (pure, no DOM, no synth)

     Same split as keys.js: arithmetic that can be tested as numbers.

     - loops.COUNT = 4, loops.ROWS = 4, loops.BAR = 16, loops.DEFAULT_BPM = 120
     - loops.create() → {steps: [], program, length}; loops.blank(n)
     - loops.stepSeconds(bpm) — a step is a 1/8 note
     - loops.quantise(elapsed, bpm) → nearest step index
     - Edits, each returning a new step array: setNote, clearCell, insertStep,
     deleteStep, padToBar

     undo / redo / canUndo / canRedo) but snapshotting the step array. It
     is re-implemented here rather than imported: history.js is text-specific
     and
     lives outside the folder sw.js caches.

     New — src/fs/pwa/bandage/smf.js (pure)

     - smf.encode(loops, bpm) → Uint8Array — a type-1 file, one MThd + one MTrk
     per loop, program change then note on/off pairs, variable-length deltas.
     - smf.fromEvents(song) → loops — turns the {t, m:[...]} events tinysynth's
     parser leaves in synth.song.ev back into steps.

     New — src/fs/pwa/bandage/recorder.js (wiring)

     - Scheduler: setInterval at 25 ms, horizon 150 ms; emits each due step at
     its exact AudioContext time with noteOn(ch, midi, 100, t) /
     noteOff(ch, midi, t + gate).
     - Play per loop: toggles that loop into the running set; starts the clock
     if
     it was stopped.
     - Record per loop: takes the current voice as the loop's program, clears
     it,
     and writes each live note into its quantised step. Other loops keep playing
     —
     that is the overdub. Pressing Record again ends it and pads to a whole bar.
     - Edit: opens the overlay described below.
     - Save / Load: smf.encode → Blob → <a download>; a hidden file input →
     synth.loadMIDI(bytes) → smf.fromEvents(synth.song), then the synth state
     (programs, master volume) is re-applied because loadMIDI resets it.

  How a tie is stored. A slot holds nothing, a note struck, or a tie — the pitch
  made negative, so a strip stays an array of numbers and a tie can never lose
  track of which note it continues:

  [ 60, -60, -60, null ]   C4 struck, held three steps, then silence
  [ 60,  60,  60, null ]   C4 struck three times over

  That distinction is the whole point. Before, those two strips were the same
  thing, which is why a held note came back as a stutter.

  One definition of what a tie means. loops.runs reads a strip as runs — a
  pitch, the step it starts on, how many steps it rings — and both the player
  and the file writer go through it. Recording writes a strike then ties
  (loops.holdNote); playback strikes once at run.at and stops at (length − 1 + 
  GATE) steps later. A held note is now one attack.

  Two edge cases it handles: a run can carry past the end of the loop and round
  to the start, which is where a punched-in part lands once the strip has been
  rotated; and a tie with nothing left to carry on — you deleted the step it
  hung off — is struck rather than dropped, so no edit silently loses a note.

  In the editor, a Tie button holds whatever was ringing in the previous step
  through this one and advances, so a note grows by tapping. A run reads across
  the row as C4 — — —, piano-roll style: the name where it's struck, the fill
  carrying through the ties.

  In the file, a run is now one MIDI note of that length rather than one note
  per step — verified through tinysynth's own parser, and a held note produces 1
  note-on/off pair where two strikes produce 2. That's also better MIDI for
  anything else opening the file.

  channels 1–8 with the hands on 0. Channel 9 is the drum channel — tinysynth
  sets rhythm[9] = 1 in reset — so a ninth loop would come out as a kit instead
  of a pitch. There's a test asserting the last loop stays below it. I also
  raised the synth from 24 voices to 48: eight loops of four notes plus two
  hands is what the app can now ask for at once, and 24 would have had it
  stealing notes back from itself.

  The table is now built, not written out. Twenty-four hand-typed buttons would
  have been a second place saying how many loops there are, and one of the two
  eventually goes wrong. So #stage keeps an empty <table id="loop_table"> shell
  and recorder.js fills it from loops.COUNT — the same arrangement as #keyboard
  and keys.layout. Changing the count is now one number. The markup test became
  a page test that checks the built table has a column per loop.

  That needed one honest improvement to the test stub: its document only knew
  about pre-registered ids, so it couldn't find elements the page creates.
  createElement now registers anything given an id, which is what a real
  document does.

  Older files still open. A .mid saved when there were four loops fills loops
  1–4 and leaves 5–8 empty — verified against a real 4-loop file and covered by
  a test.

  One thing to flag: eight columns across a third of a phone in portrait is 
  tight. At 375px wide, after the row labels, each button is roughly 38px —
  under the 44px that thumbs like. It works, and landscape is comfortable, but I
  shrank the label column and the glyph size to buy the room. If it turns out
  too cramped in the hand, the fix is a different panel layout (two banks of
  four, or a wider stage), not a smaller font — I've noted that in PLAN.md under
  what's not done.

  And the standing caveat: still no browser in this session, so the eight-column
  density is reasoned from the CSS rather than seen. That's the one thing here
  I'd want you to eyeball on a real phone.
