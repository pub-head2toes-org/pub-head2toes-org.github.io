  What the page does

  - Sign-in: a visitor without a live Northern session is sent to Reg.html and
    returned afterwards, invite included.
  - Layout: signed-in user, invite link, the three panels (Pals, Log, Groups
    over Group members), then Incoming messages, as in PROMPT.md.
  - Storage: pals, groups and messages are kept in local storage, per identity,
    in plain text for now.
  - Push: sw.js passes a push on to the page, which puts the sender on top of
    the incoming list; nothing can send one yet.

  Things you might not expect:
  - The page writes to the database when opened. Northern has no route for
    <host>/<key>, so the page posts one public row at that address that forwards
    to Pals. Northern cannot delete rows, so it is permanent.
  - The key in the invite link is base64url, because most keys contain a /.
  - The lists are not real <textarea>s, since a text area can't hold the
    coloured oval or a two-row entry. The overlay showing a whole message is
    one.
  - Selecting a pal also loads the Log, and the panels stack on a phone.

  Architecture findings (PLAN.md)

  - The Northern key works as a VAPID key. It is the same curve and signature,
    and a token signed with it verifies the way a push service checks it. But
    VAPID only restricts who may use a subscription; the receiver never sees it.
    Using it to identify the sender means one service worker registration per
    pal.
  - Both options are blocked on the private key. Northern deliberately keeps no
    key in the page after Reg.html, and both options need to sign and decrypt. I
    recommend a per-device key in IndexedDB, certified once by the ID Card.
  - Option 2 is not possible on Northern today. There is no DELETE, an overwrite
    keeps the old value readable, a mailbox can't be made private to its
    receiver, and listings name every sender.
  - Option 1 only works when both pals are in the app at once, because a service
    worker can't hold the /sub/ stream.
  - Same-origin risk: anyone can publish a page on the origin Pals runs on, and
    script there can use everything Pals has. The zero-trust claim doesn't hold
    under either option until Pals has its own origin.

  My recommendation is to build the message envelope and an outbox with
  acknowledgements once, then add carriers in order: option 1, then a variant
  where short messages ride inside the push payload itself (nothing stored on
  Northern, and the pal can be offline), and option 2 only if that leaves a gap.

  How a message travels:
  - Sending: the page looks up the pal's device under /pals/ and posts the text
    to /push/api/send. The server takes the sender from the verified cookie,
    seals the message with a key derived from its VAPID key and the receiver's
    key, and sends it through the receiver's push service. Nothing is stored on
    Northern.
  - Receiving: the service worker saves each push in IndexedDB first, opens it
    through /push/api/open if the session is still valid, and always shows a
    notification. The notification names the sender, never the text, and the
    page files the message.
  - Long messages: they are split into parts of at most 1000 characters (and
    3200 bytes, because 1000 emoji don't fit in one push). The receiver puts
    them back together in any order.
  - Delivery: each message shows sending… or not delivered, with the reason and
    a Send again button.
  - The pals. host: a host starting with pals. was useless as its own origin,
    because Northern serves anyone's database rows as HTML on every host. So on
    that host, every page other than Pals and the sign-in pages is now sent
    sandboxed, with no script. Other hosts behave as before.

  Where I read UPDATE_1.md in a particular way (each is explained in PLAN.md):
  1. /push/api/send also needs to, the receiver's key: the listed inputs don't
     say whose key to seal to.
  2. "Verify the sender pub key matches the current user" under open is checked
     as "the message is addressed to the caller". The sender is checked against
     the cookie when it sends.
  3. The key in /pals/<username>/<key> is in base64url, because three keys in
     four contain a /.
  4. welcome.html updates an existing row in place first, then creates it if

  5. A group message arriving for a group the receiver doesn't have creates that

  Trade-offs that come with this design:
  - The server sees every message, and the receiver has only the server's word
    for who sent it. This is not the zero-trust channel from PROMPT.md.
  - Anyone signed in can message anyone on the list.
  - The newest device row wins, so each user effectively has one device.
  - The server doesn't check how old a session cookie is.
  - A direct message that starts with [something]  is filed as a group message.
