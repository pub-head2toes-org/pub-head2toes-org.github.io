● UPDATE_3 is implemented in src/fs/reg/Reg.html (plus its stylesheet, tests and
  docs). Full suite: 243 tests, 0 fail (4 pre-existing todos).

  What changed

  Header — one banner, pub.head2toes.org. The second head2toes header is gone.

  Message section (src/fs/reg/Reg.html:26) — the textarea is now a real element
  in the markup, readonly, full page width. Every message goes through a say()
  helper that sets its value; nothing injects <textarea> via innerHTML any more.

  Sign section (Reg.html:33) — has its own optional passphrase field
  (signin_passphrase, autocomplete="current-password"), used only to decrypt a
  card being loaded. The control reads Load Id Card & Continue, and it now
  actually continues: on a successful load the page navigates to the fragment
  path (/fs/get/home.html by default).

  Reg section (Reg.html:50) — user name, passphrase, repeat passphrase, plus a
  new read-only pubkey field showing the public half (never the private one).
  Save Id Card & Continue is the only button; the Continue link is removed.

  The one behaviour I split deliberately: the single passphrase field was doing
  double duty for load and save, which is the confusion the update names.
  getSignInPassphrase() feeds idcard.open, getPassphrase() feeds idcard.toFile.

  One gap worth knowing about — with Continue gone, a visitor whose cookie is
  still live who opens Reg.html by hand has no button that moves them on; both
  remaining controls need a file. Anyone the server redirects here has no
  cookie, so the normal paths are fine. I wrote it up as REFACTORING #25 with
  the fix I'd pick (a Continue as <name> button in the Sign in section, shown
  only while session.signedIn()) rather than adding UI the update didn't ask
  for. Say the word and I'll add it.

  Tests — tests/Reg.test.js gained a layout suite asserting the UPDATE_3
  structure against the real markup (one h1, the three headings in order,
  readonly board, separate passphrases, no #next, readonly pubkey field), plus
  tests for the pub-key field and for navigation-on-load. The old assertions
  moved from msg.innerHTML to msg.value. Signin.html was not in scope and is
  untouched.

● Fixed. 257 tests, 0 fail (the same 4 pre-existing todos).

  The bug — Save Id Card called session.card(), which throws load your ID Card 
  first whenever the key isn't in memory. A live cookie is not a loaded key, so
  every signed-in visitor without their card hit it, while the field showed the
  session's public key it could never save.

  The fix — session.js gained two pieces (src/fs/reg/session.js:86): draft()
  generates a key pair that is held nowhere and stored nowhere, and adopt()
  makes a drafted pair the browser's identity. generate() is now just those two
  together, so the first-visit path is unchanged.

  Reg.html drafts a pair on every load (currentDraft(), after the remotectrl
  redirect so it isn't wasted). The read-only field shows what Save would
  actually write — the loaded card's key when one is loaded, the draft
  otherwise. Save builds the card from that same pair, and only after the file
  is successfully built does it adopt the pair, re-sign the cookie and register
  it. A failed build (mismatched passphrases, encryption error) changes nothing
  at all — the signed-in identity survives untouched.

  Saving while signed in therefore replaces the identity, which is what the Reg
  section means. Both message-board texts now say so: "The ID Card below is a 
  new identity - saving it replaces this one", and for an expired session, "or 
  save the ID Card below to register as somebody new". The old identity's card
  file still opens normally.

  UNKNOWN — session.rememberUserName now stores UNKNOWN instead of deleting
  pub_name when the field is empty. Since userName() reads storage, that name
  flows through consistently: the DB record is {pub, pub_name: "UNKNOWN"} and
  the download is UNKNOWN.20260816T….id.txt rather than a bare timestamp.

  One related thing I fixed while in unlock(): loading an unnamed v1 card used
  to leave whatever pub_name was already stored, so the previous user's name
  could end up attached to a different public key. It now keeps the stored name
  only when the card is that same key, and otherwise sets UNKNOWN.

  Tests — nine new ones, mostly in a new Reg.html saving without a card loaded
  suite: the draft gets saved with its private half, it matches the key shown in
  the field, it becomes the stored/registered/cookie-signing identity, a failed
  build leaves the signed-in identity alone, the expired-session case works
  too, and a loaded card still wins over the draft. Four existing tests changed
  to the new behaviour (the pub-key field, the two UNKNOWN naming cases, and the
  old "cannot save" test, which asserted exactly the bug you reported).
