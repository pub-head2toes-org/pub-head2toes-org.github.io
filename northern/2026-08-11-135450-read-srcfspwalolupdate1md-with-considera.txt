● Read UPDATE_1.md plus the current Phase 1 implementation (lol.js, PLAN.md) to
  see what's already in place. Two of the three Phase 2 asks are largely
  satisfied already: move/join envelopes over PUT+SSE and a per-instance state
  object are exactly what Phase 1 built. The genuinely new pieces are the
  persistent KV DB (nothing in joint/rummy uses it yet — this is a fresh
  integration) and NPC bots.

  Key considerations:

  - Late-joiner gap the KV DB should fix: Phase 1's peer-broadcast model means a
  client only learns about other players from live SSE messages — if you join
  mid-session, you don't see anyone until they move again. The new REST DB
  (POST/PUT/GET, path-as-key) is the natural fix: each client also writes its
  own location to a durable key (e.g. /lol/<sse-channel>/players/<name>) on
  join/move, and a joining client does a GET over that namespace to seed
  state.players immediately, with SSE staying the live-update path. That keeps
  the current "no organizer authority" model intact — each client still only
  ever writes its own record.
  - /fs/get is read-only server-file data, not a fit for dynamic player state —
  probably more relevant later for static config like NPC definitions or map
  metadata.
  - NPC bots run outside the browser: "standalone HTTP and SSE client" means
  Node, not another browser tab. Node has global fetch but not EventSource —
  needs the eventsource package (or similar). The bot should reuse the exact
  same join/move envelope shape Phase 1 already emits, so existing clients
  render it with zero special-casing.
  - Bot behavior (roam/remember/favorite/follow/switch) is a small local state
  machine keyed off the same SSE stream a real client listens to — no new
  server-side concept needed, just a client that decides its own target instead
  of taking pointer input.

  code, or go straight to scoping/building the DB-backed player-state bootstrap
  first?

● UPDATE_2.md substantially revises the Phase 2 design I already drafted into
  PLAN.md — worth flagging the contradictions before we touch code again:

  - KV DB deferred entirely. "DB to be used only for specific use-cases...
  persisting game state in KV DB can be developed at some later phase." This
  kills addendum decisions 11–14 and build steps 1/3/4 — no bootstrap GET, no
  per-player PUT to a KV path, no DB_HOST/path-convention questions to resolve.
  Movement stays SSE-only this phase, confirmed explicitly ("Movement updates to
  be shared only through the SSE channel in this phase").
  - Late-joiner bootstrap moves to SSE itself, not a DB read. UPDATE_2 offers
  two mechanisms: a joining client can ask over the SSE channel for a state
  update and get replies from each participant as SSE events, or just wait for
  the new periodic heartbeat below. This needs a new envelope type (e.g.
  state_request, answered by each peer with its current move) — I hadn't
  designed this in the addendum.
  - New requirement: idle heartbeat. Today updateLocalPlayer only broadcasts
  while walking (throttled) plus one final stop message — a stationary player
  goes silent. UPDATE_2 requires periodic re-emission of current position even
  while stationary, with the gap between updates under 500ms. This is a real
  change to the broadcast loop, not just a new envelope type.
  - "All participants disconnect → state resets" isn't something to build — it's
  confirming the no-persistence peer-only model is intentional (nothing
  survives a full dropout, and that's fine since there's no DB backing it this
  phase). Just a clarification, not a task.
  - NPC bots are a much simpler, different shape than I drafted. UPDATE_2 wants
  them in-browser, not a standalone Node/eventsource client:
    - One example bot, "Winnie," in bots.js at the lol/ root, <script>-included
  in index.html.
    - Bot "prototype" is a plain object with init/move functions, namespaced as
  Bot.Winnie.
    - The page's own game loop (a setInterval) calls init once and move
  periodically for any bot whose Bot.<name> pattern appears in the participants
  list — so a bot runs inside the same tab as a second virtual participant, not
  as a separate process.

  This replaces addendum decisions 15–18 and the bots/npc-client.js +
  bots/pet-robot.js file plan wholesale — no Node, no eventsource package, no
  separate CLI-driven process, no generic pluggable-behavior base class (at
  least not yet, with only one bot to support).

  One open question this raises that UPDATE_2 doesn't fully resolve: when
  Bot.Winnie is in participants and the game loop spawns it, what name does it
  broadcast as in join/move envelopes — "Bot.Winnie" verbatim, or "Winnie" with
  the Bot. prefix stripped for the on-map label? I'd default to stripping it for
  the visible name, but worth confirming before I bake it into the addendum.

  DB/Node-bot sections, add the SSE state-request + heartbeat design and the
